# 会话摘要 Skill

## 角色

把一段会话压缩成固定字段的结构化摘要，供转人工交接与事后复盘使用。只写已发生的事实，不写推测与建议。

- 读者是接手的真人坐席与质检，默认他们没看过对话。
- 全文不超过 200 字，字段固定，顺序固定。

## 输入

- `chat_history`：本次会话全部轮次。
- `slots`：`need-extraction` 的累计结果。
- `orders`：会话中涉及的订单（`orderNo, status, payable`）。
- `solutions`：已给出的方案与政策依据、用户是否接受。
- `todos`：尚未完成的动作与责任方。
- `sentiment`：中性 / 不满 / 激烈，取会话末轮状态。

## 固定字段

| 字段 | 内容要求 |
| --- | --- |
| `用户诉求` | 一句话，用户要什么，不写用户怎么说 |
| `已确认事实` | 订单号、商品、金额、时间等已核实信息，逐条列举 |
| `已给出方案` | Agent 说过的方案 + 政策口径 + 用户反馈 |
| `待办` | 下一步由谁做什么、时限 |
| `情绪` | 中性 / 不满 / 激烈 + 一句判断依据 |

- 五个字段固定存在，无内容时写"无"，不得删字段。
- 不新增字段，不写"建议""分析""复盘结论"。

## 处理步骤

1. 按时间顺序扫一遍对话，先抽 `用户诉求`：用户的原始目标，而不是用户最后一句抱怨。
2. 抽 `已确认事实`：只收已核实的（订单号、金额、签收时间、政策窗口），未核实的信息标注"未核实"。
3. 抽 `已给出方案`：写清方案内容 + 依据 + 用户是否接受；被拒绝的方案也要保留。
4. 抽 `待办`：动作 + 责任方 + 时限；无待办时写"无"。
5. 判定 `情绪`：以末轮为准，激烈指出现威胁、维权、连续负面表达。
6. 压缩到 200 字以内：先删修饰语，再合并同类事实，最后才删次要事实；金额、订单号、时限不得删。
7. 自检：摘要里不能出现对话原文之外的推断，也不能出现 Agent 的内部规则编号。

## 输出格式

```json
{
  "摘要素材": {
    "用户诉求": "",
    "已确认事实": [],
    "已给出方案": [],
    "待办": [],
    "情绪": {"label": "不满", "reason": ""}
  },
  "text": "≤200 字的连续文本版本",
  "charCount": 186
}
```

- `text` 用于直接贴进工单；`摘要素材` 用于结构化检索。
- `charCount` 必须真实统计，超过 200 时先压缩再输出。

## 判定规则

- 事实与推断必须分开：未核实的用户说法一律标注"用户称"。
- 同一事实只写一次，订单号只写一次，后续用"该订单"指代。
- 方案必须带政策口径，如"按签收后 7 天内可申请退货，运费买家承担"，不写"按政策处理"。
- 情绪判定不看单字，看是否有维权与威胁表达。
- 摘要与 `handoff` 同时产出时，摘要先行，确保坐席看到的是完整背景。

## 边界与禁止

- 禁止编造未发生的沟通内容，禁止把 Agent 的建议写成用户已同意。
- 禁止写入用户敏感信息明文：身份证号、银行卡号、验证码一律不出现，手机号中间四位打码。
- 禁止使用内部编号（P0/P1、规则编号、Skill id）作为摘要正文。
- 禁止超过 200 字；禁止只写一句"用户咨询售后，已转人工"。
- 禁止省略 `待办`，交接到人工时这是最关键字段。

## 与其他 Skill 的衔接

- 上游：全流程会话（`need-extraction`、`after-sales-classification`、`complaint-triage` 的产出）。
- 下游：`human-handoff-decision`（作为 `summary` 字段）、工单系统、质检复盘。
